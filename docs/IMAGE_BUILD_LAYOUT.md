# Image Build Source And Artifact Layout

This document defines the layout for image build inputs and generated outputs.
Source fixtures live under `packer/`; machine-created Ignition, HTTP installer
payloads, and Packer manifests live under `build/` and are ignored by default.

## Layout Contract

| Content | Target Location | Source Or Generated | Notes |
| :--- | :--- | :--- | :--- |
| Packer HCL templates | `packer/*.pkr.hcl` | Source | Reviewed build definitions for each supported image family. Current templates include `packer/ubuntu2404.pkr.hcl`, `packer/photon.pkr.hcl`, and `packer/fcos.pkr.hcl`. |
| Packer HTTP source content | `packer/http/<image>/` | Source fixture or template input | Static installer inputs that Packer serves during a build, such as Ubuntu autoinstall `user-data` and `meta-data`, belong here when they are intentionally tracked and sanitized. |
| Butane source templates | `packer/butane/<image>/` or generated in code under `src/homelab_gitops/immutable/` | Source | Human-authored FCOS source YAML belongs under a source directory, not beside generated Ignition. Dynamic Butane generated by `ButaneTranspiler` remains code-owned until a separate issue extracts templates. |
| Generated Ignition | `build/ignition/<profile-or-image>/` | Generated output | Ignition JSON emitted from Butane should be treated as build output. It can contain host-specific networking, SSH keys, bootstrap content, or other transient values. |
| Generated HTTP installer content | `build/http/<image>/` | Generated output | Per-run installer payloads copied or rendered for Packer's HTTP server belong here. Packer can then point `http_directory` at this generated directory. |
| Packer build manifests and logs | `build/packer/<image>/` | Generated output | Machine-created build metadata should stay outside source directories unless converted into a reviewed fixture. |

## Reconciled State

Issue #82 removed generated FCOS installer artifacts from source paths and
updated Packer to serve generated installer content from `build/http/fcos/`.
These paths are intentionally treated as generated outputs:

| Generated Path | Treatment |
| :--- | :--- |
| `build/http/fcos/installed.ign` | Per-run FCOS installer payload served by Packer. Regenerate locally before FCOS image builds; do not commit. |
| `build/ignition/fcos/` | Generated FCOS Ignition JSON from Butane transpilation. Do not commit. |

## Packer And Butane Reference Points

`PackerDriver` currently resolves templates from `packer/<os_type>.pkr.hcl`
with fallbacks to `packer/photon.pkr.hcl` and `packer/ubuntu2404.pkr.hcl`.
That keeps Packer HCL under `packer/`.

`packer/fcos.pkr.hcl` sets
`http_directory = "${path.root}/../build/http/fcos"` and boots FCOS with
`coreos.inst.ignition_url=http://{{ .HTTPIP }}:{{ .HTTPPort }}/installed.ign`.
The `installed.ign` file is a generated HTTP installer payload and should be
created under `build/http/fcos/` before running an FCOS image build.

`ButaneTranspiler` currently builds FCOS Butane YAML in Python and returns
Ignition JSON from `butane --strict`. Until templates are extracted, its output
should be considered generated Ignition and should not be committed as ordinary
source.

## Smoke Validation

Run the image build input smoke validator after changing Packer templates,
Packer HTTP fixtures, or Butane transpilation logic:

```bash
python3 scripts/validate_image_build_inputs.py
```

The validator runs `packer init` and `packer validate` for each
`packer/*.pkr.hcl` template with non-secret placeholder variables, then
transpiles a sample FCOS profile through `butane --strict`. It validates local
inputs only; it does not build images, contact vCenter, or deploy
infrastructure. The same command can be used as a CI gate on runners that have
Packer and Butane installed.

## Cleanup Rules

1. Keep source templates and generated output in separate top-level trees:
   `packer/` for reviewed image-build source, `build/` for machine output.
2. Do not commit generated Ignition or per-run HTTP installer payloads unless a
   future issue explicitly converts a sanitized file into a fixture.
3. When moving files in a later cleanup issue, update Packer `http_directory`
   and installer URLs in the same change.
4. Keep generated `build/http/`, `build/ignition/`, and `build/packer/`
   contents out of commits unless a later issue explicitly documents a
   sanitized fixture.
